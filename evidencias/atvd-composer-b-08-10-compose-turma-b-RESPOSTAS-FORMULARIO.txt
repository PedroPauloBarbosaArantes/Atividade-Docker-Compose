================================================================================
Falhas encontradas
================================================================================

Falha 1 — proxy do portal aponta para 127.0.0.1 em vez do serviço api

Sintoma: página em :8081 abre, mas /api/* devolve 502. Estado da API não fica "ok".

Comando/log da causa:
  docker compose exec portal cat /etc/nginx/conf.d/default.conf
    set $destino http://127.0.0.1:3000;
  docker compose logs portal
    connect() failed (111: Connection refused) ... upstream: "http://127.0.0.1:3000/saude"

Causa: API_URL=http://127.0.0.1:3000. Dentro do container portal, 127.0.0.1 é o próprio Nginx, não a API. Na rede do Compose o hostname correto é o nome do serviço (api).

Hipótese testada e descartada: containers não estavam rodando. docker compose ps mostrou os dois Up. A página HTTP 200 confirma que o portal atende.

Alteração: API_URL: "http://api:3000"

---

Falha 2 — porta da API (3001) diferente da porta usada pelo portal (3000)

Sintoma: depois de corrigir só o hostname, /api/saude continuou 502.

Comando/log da causa:
  docker compose logs api
    {"evento":"inicio","porta":3001}
  docker compose logs portal (após API_URL=http://api:3000)
    connect() failed (111: Connection refused) ... upstream: "http://172.18.0.2:3000/saude"

Causa: o Nginx passou a resolver o serviço api (IP 172.18.0.2), mas tentou a porta 3000. A API escuta em PORT=3001.

Hipótese testada e descartada: o nome DNS "api" não existiria. O log mostra upstream no IP do container da API (172.18.0.2), então a resolução funcionou; o recusou foi a porta.

Alteração: PORT: "3000" (alinhado ao Dockerfile EXPOSE 3000 e ao API_URL).

Depois disso:
  GET /api/saude  -> 200 {"status":"ok","turma":"B"}
  GET /api/livros -> 200 com total: 3 e os três títulos.

---

Falha 3 — reservas não sobrevivem a docker compose down / up

Sintoma: POST /api/reservas retornou 201 e a página listou a reserva, reduzindo restantes de 3 para 2. Após docker compose down e docker compose up -d, GET /api/reservas voltou [].

Comando/log da causa:
  (antes do volume nomeado)
  GET /api/reservas após down/up -> []  HTTP 200
  A API grava em /app/registros/reservas.json (server.ts). O compose só montava ./dados:/app/dados:ro. docker compose down apaga o filesystem do container.

Hipótese testada e descartada: o bind :ro de dados impediria gravar a reserva. A gravação é em /app/registros, não em dados. O POST 201 com o volume ainda inexistente mostrou que a escrita no diretório interno do container funcionava; o que falhava era a persistência entre down/up.

Hipótese descartada também: publicar a porta da API. docker compose ps manteve a API só em 3000/tcp interno. curl em 127.0.0.1:3000 e :3001 falhou (Could not connect), atendendo o critério 4.

Alteração: volume nomeado registros montado em /app/registros.

================================================================================
Conteúdo final do compose.yaml
================================================================================
services:
  api:
    build: ./api
    environment:
      PORT: "3000"
    volumes:
      - ./dados:/app/dados:ro
      - registros:/app/registros
  portal:
    build: ./portal
    ports:
      - "127.0.0.1:8081:80"
    environment:
      API_URL: "http://api:3000"
    depends_on:
      - api

volumes:
  registros:
